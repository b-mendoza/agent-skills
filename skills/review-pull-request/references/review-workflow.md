# Review Workflow

> Read this file after input normalization, before dispatch. This is the single normative source of phase order, routing, repair, approval and terminal behavior. The entrypoint's overview is illustrative. Raw diffs, source, API replies and fetched pages stay with the inspecting role; the orchestrator retains bounded results and user decisions.

## State And Counters

Carry inputs, resolved `SKILL_DIR`, identical `MUTATION_LIMITS`, selected output path/content identity, pinned `REVIEWED_BASE_SHA`/`REVIEWED_HEAD_SHA`, PR state, declared dimension order, joined coverage/results, typed history availability, complete canonical package, verification, exact approval and actual posting receipts. Do not add a checkpoint file, posting journal or serialized resume format.

| Counter                   | Cap | Consumed by and exhausted route                                                    |
| ------------------------- | --- | ---------------------------------------------------------------------------------- |
| `CONTEXT_RETRY`           | 1   | Narrow missing-context requests across context/chunks/verify; then `NEEDS_CONTEXT` |
| `METADATA_RETRY`          | 1   | `COMMENTS: NEEDS_METADATA` collection/draft retry; then `REVIEW_ERROR`             |
| `OUTPUT_REPAIR[dispatch]` | 1   | Invalid/missing read-only result or lost worker; then phase ERROR                  |
| `VERIFIER_REPAIR`         | 2   | `VERIFY: FAIL` repair cascades; third failure becomes `VERIFY_FAIL`                |
| `GATE_REASK[checkpoint]`  | 1   | Ambiguous checkpoint response; second ambiguity or no answer is `BLOCKED`          |

A dispatch counter belongs to the logical phase/dimension invocation and survives its repair redispatch. A writer result uses the same one-output-repair allowance only after read-only inspection of the named artifact; never replay its write blindly. A poster result has no mutation retry allowance: reconcile read-only in one recovery pass. Malformed/lost recovery output uses `OUTPUT_REPAIR[reconciliation]` once to repair only that read-only report; exhaustion or unavailable recovery capability stops with `POST_ERROR` and explicit uncertainty. Never loop back into posting. Human-requested revisions are external events, not automatic repairs; a new verified revision starts a new verifier-repair allowance, never reuses approval and is not capped by earlier human edits.

## Result Grammar And Consumer Gate

Each role's Output Format declares exact fields/order and conditional fields. Actual results contain the block alone, without an outer code fence, leading prose or `see above`. Status/scalar lines are nonempty `Key: value` on one source line. Lists start on the line after `Key:`; empty lists are exactly `- none` at that list's indentation. A nonempty list never mixes `none` with records. Record fields use the indentation shown in the producer contract. IDs and list entries are unique within their declared scope; counts are base-10 nonnegative integers. Full SHAs are 40 hexadecimal characters; SHA-256 values are 64. A line range is a positive integer or inclusive `N-M`, with `N <= M`. Booleans are literal `true`/`false`; null is literal `null`, distinct from an unavailable field.

For exact Markdown blocks, every content line, including blank lines, has the shown two-space summary or four-space Body container indent. Remove exactly that indent and nothing else. Each content line ends in LF, including the final line; preserve any additional trailing blank lines. Scalars/record delimiters are unindented or less-indented as shown, so content cannot become a routed field. Prose paragraphs have one source line; code/list/suggestion structure may span lines intentionally. Body text is opaque exact Markdown to the checker, not evidence of semantic truth.

Before using any fields, the consumer runs the self-test as a separate step:

```sh
python3 -I "${SKILL_DIR}/scripts/validate-output.py" --self-test
```

If it fails, treat the checker as unavailable and raise `TOOLS_MISSING`, never output repair. Only after it passes, run the payload check separately:

```sh
python3 -I "${SKILL_DIR}/scripts/validate-output.py" <mode> < "$payload"
```

Route only on the payload check's exit status. One literal mode is `context|chunk|adjudicate|comments|verify|write|post`, matching the producer. Exit 0 accepts shape only. Exit 1 emits findings and takes output repair; exit 2 is a bad invocation and takes that phase's ERROR route. If the shell/interpreter/checker cannot run, the orchestrator raises `TOOLS_MISSING` itself without consuming result fields. A producer's validation claim never satisfies this gate. Safe stdin is preferred; a necessary payload file must be bounded, proven ignored and run-local under the intake envelope. Never interpolate evidence as shell code, persist secrets/full diffs/raw logs, or clean another run's files.

## Helper Exit Routes

The collector invokes `sh "${SKILL_DIR}/scripts/collect-pr-review-comments.sh" [--dry-run] <PR_URL>` read-only. Exit 0 means complete outer reads; zero records is known-empty threads. Exit 3 supplies valid records but truncated inner history, so history is `partial` and required history routes `CONTEXT: NEEDS_CONTEXT`. Exit 2 → `CONTEXT: TOOLS_MISSING`; 4 → `CONTEXT: AUTH`; 1/64/65 → unknown history and `CONTEXT: ERROR`. Null root IDs fail the helper with exit 1; it buffers all pages and emits nothing after a failed read. Exit-3 partial history may support a limited draft-only packet; optional unavailable top-level feedback may likewise be disclosed. Neither exception overrides the helper's 1/2/4/64/65 routes or establishes complete/empty history. Top-level reviews/discussion remain separate collector reads. `--dry-run` prints its command/query/filter without calling GitHub; it is the runnable check, not history evidence.

The summary helper is `sh "${SKILL_DIR}/scripts/post-pr-review.sh" [--dry-run] <owner>/<repo> <number> <APPROVE|REQUEST_CHANGES|COMMENT> <body-file> <reviewed-head-sha>`. Normal execution creates the exact approved review with `commit_id`; dry-run prints method/endpoint/event/commit_id/exact body without network. Exit 0 → read-back; 2 → `POST: TOOLS_MISSING`; 4 → `POST: AUTH`; 64/65/66 → `POST: ERROR`. Exit 1 may follow a live write, so row 1 always applies, never helper replay. Confirmed effects plus failure use `POST: PARTIAL` instead of hiding effects behind preflight statuses. Both scripts accept `-h`; their body/payload lifecycle stays within the run-local envelope.

## Final Preview And Re-entry

The final preview contains exact GitHub event, summary and every body, pinned comparison/head, PR state/historical label, actual new-inline line metadata, helper-paired thread/root IDs and root URLs, expected resolved state/capability, each planned unresolve/reply, checks passed and material residual risks. Show a supplied known matching approval in Notes if relevant; add no approval poller. Explain that ABORT preserves the draft and posts nothing. APPROVED applies only to that preview. REVISE returns to existing owners. Missing approval never posts.

Saved-review re-entry uses the selected artifact as an untrusted bounded evidence reference for existing collector/adjudicator/drafter/verifier owners, not a new resume file. Recover complete records, exact summary/bodies, basis and inspection limits; refresh mutable evidence. If recoverable evidence does not support the new request or version, perform a fresh full review. An existing artifact can be replaced only at its exact content-bound checkpoint, otherwise select an unused output path. Receipt updates have narrower authority than replacement: only posting status and the reserved receipt may change.

## Terminal Outcomes And Final Output Contract

Closed `PR_REVIEW` success set: `VERIFIED_DRAFT_SAVED | VERIFIED_DRAFT_SAVED_POSTING_CANCELLED | VERIFIED_REVIEW_POSTED`.

Every success reply ends with this block. Notes name meaningful observed checks, material omissions, degraded isolation, stale-artifact warnings and available live URLs, rather than claiming checks from links alone.

```text
Review file: <OUTPUT_FILE>
Findings: <nonnegative integer>
New comments: <nonnegative integer>
Follow-up replies: <nonnegative integer>
Review decision: <comment | request changes | approve>
Posting: <skipped | posted | cancelled>
Notes: <observed evidence/limits/live URLs or none>
PR_REVIEW: <VERIFIED_DRAFT_SAVED | VERIFIED_DRAFT_SAVED_POSTING_CANCELLED | VERIFIED_REVIEW_POSTED>
```

Closed failure set: `AUTH | NOT_FOUND | NEEDS_CONTEXT | REVIEW_ERROR | VERIFY_FAIL | WRITE_ERROR | POST_ERROR | TOOLS_MISSING | BLOCKED`. Every failure reply ends with:

```text
Review file: <OUTPUT_FILE or none>
Posting: <skipped | posted | cancelled | failed | partial | uncertain>
Notes: <observed checks, omissions, actual effects/live URLs and artifact warning, or none>
PR_REVIEW: <AUTH | NOT_FOUND | NEEDS_CONTEXT | REVIEW_ERROR | VERIFY_FAIL | WRITE_ERROR | POST_ERROR | TOOLS_MISSING | BLOCKED>
Reason: <one-line cause>
Next step: <one clear safe action>
```

GitHub outcome has priority over artifact update: posted stays posted with live URLs, cancellation stays cancelled, and failed/partial/uncertain actions retain actual effects even when recording failed status also fails. Never claim external effects were rolled back.

## Dispatch Example

A two-dimension run joins in declared order, adjudicates three confirmed findings and two drops, then drafts one new inline comment and two follow-ups. One follow-up has an explicit approved reopen-and-reply pair. Verification checks the same complete package and current basis. The writer saves a create-only draft. Final preview names all actions and exact text; APPROVED permits one poster dispatch. The review posts first, then the approved reopen immediately before its reply. Read-back supplies URLs and confirmed reopen outcome; a writer receipt failure still ends `PR_REVIEW: VERIFIED_REVIEW_POSTED` with a stale-artifact warning.
